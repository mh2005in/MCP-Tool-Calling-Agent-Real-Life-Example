# F41-01 — Inspect and classify every source PDF

**Status:** PARTIAL
**Priority / Effort:** P0 / M
**Phase:** 1 (stages 1.1–1.2) — [Plan.md](../Plan.md) §5
**Source:** [`../input/pending/Section-4.1-XFA-Real-PDF-Onboarding-Issue.md`](../input/pending/) §5
**Depends on:** —
**Blocks:** `F41-02`, `F41-12`, `F41-14`, `GAP-01` completion

## Requirement

Every governed source PDF is inspected and classified by **form technology**, and that classification
— not a guess — decides whether the system offers auto-fill or manual upload.

> **No dynamic-XFA form may ever be marked fillable.** Emitting a blank-but-"successful" PDF that a
> consultant might file is a trust failure, not a missing feature (Phase 5 §4.1).

This is a correctness gate, not a feature. It is the control that makes [ADR-002](../design/ADR-002-xfa-engine-deferred.md)'s
"degrade usefully" position safe.

## Acceptance criteria

- [ ] A `FormTechnology` enum exists with `STANDARD_ACROFORM`, `STATIC_XFA`, `DYNAMIC_XFA`, `NONE`
- [ ] `PdfInspectionResult` carries the classification, not just a `hasXfa` boolean
- [ ] `PdfBoxFormEngine.inspect` distinguishes **static** XFA (fillable via the AcroForm layer) from **dynamic** XFA (not fillable) by examining the XFA packet, not merely its presence
- [ ] Barcode fields are detected and `FormDefinition.supportsBarcode` is set accordingly
- [ ] Classification is persisted on `FormDefinition` and returned by `GET /v1/forms/{formId}`
- [ ] `DYNAMIC_XFA` **or** `supportsBarcode = true` ⇒ `status = BLOCKED` and `supportsFill = false`, with no override path in the API
- [ ] `sourceSha256` is recorded at inspection; a changed hash forces re-inspection before generation
- [ ] `CaseFormGenerationService` refuses to generate for any form not classified in this run's schema version
- [ ] A round-trip fixture per classified form: fill → reopen → assert values present and the file opens
- [ ] The catalogue UI surfaces the technology, not just fillable-vs-blocked (`F41-11` renders the badge; this supplies the value)

| `FormStatus` enum with `BLOCKED` | `enums/FormStatus.java` — `DRAFT`, `ACTIVE`, `RETIRED`, `BLOCKED` |

| Field discovery and sync | `FormCatalogueService.inspectForm()` :114 — upserts `FormFieldDefinition` per discovered field |
| Blocked-form handling downstream | `CaseFormGenerationService` skips forms where `supportsFill = false`; `PackageValidationService` :207 suppresses field noise for uploaded forms |
| Hash-mismatch guard at generation | `CaseFormGenerationService` :285 — `FORM_SOURCE_HASH_MISMATCH` |

**Missing.**

| Gap | Consequence |
| --- | --- |
| **No `FormTechnology` enum.** The 17 enums in `enums/` do not include one | Classification has nowhere to live. `hasXfa` is the entire model |
| **Static and dynamic XFA are indistinguishable.** `acroForm.getXFA() != null` is true for both | A *static* XFA form is fillable through the AcroForm layer and is being treated as equivalent to a dynamic one — either over-blocking or, if the operator overrides `supportsFill`, silently producing an invalid file |
| **`supportsBarcode` is never written.** The field exists; nothing sets it | Barcode forms — which Adobe must regenerate on save — can be marked fillable |
| **`supportsFill` is operator-settable without classification evidence** | The safety property depends on an admin not checking a box. Not a control |
| **No round-trip fixture** | "Fillable" is asserted, never demonstrated. `DR-10` |
| **Hash mismatch is enforced at generation only** | The readiness layer reports a package as ready when its form source has changed underneath it |

## Why this is the phase's first item

The rest of Phase 1 rests on it. `F41-02`'s data-sheet fallback is defined as "the path for `BLOCKED`
forms" — which requires knowing which forms are blocked *and being right*. `F41-12`'s admin editors
expose fill configuration to an operator, which is unsafe while `supportsFill` is a free-form
checkbox. And `F41-14`, if `D-1` ever unblocks it, selects an engine **by form technology** — the
value this requirement produces.

## Implementation note

`PdfFormEngine` is an SPI with one implementation. The classification belongs in `PdfInspectionResult`
so that a future commercial engine reports technology the same way, and `FormCatalogueService` stays
engine-agnostic. Distinguishing static from dynamic XFA means reading the XFA packet — the
`config` / `template` streams indicate whether the form requires the dynamic layout engine — rather
than testing the packet for existence.

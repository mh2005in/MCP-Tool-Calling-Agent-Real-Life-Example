# Issue: Real IRCC PDF onboarding — XFA dynamic forms cannot be filled by PDFBox

- **Area:** Section 4.1 form automation · backend `com.immiauto.service.forms.pdf` + form catalogue
- **Severity:** High (blocks the core value of the feature for most high-volume forms)
- **Status:** Open / deferred (M3 shipped on a synthetic AcroForm; no real IRCC form is fillable yet)
- **Related:** [Section 4.1 Implementation Plan](Section-4.1-IRCC-Form-Package-Automation-Implementation-Plan.md) §13 (risks), backlog item #1

## 1. Summary
The generation pipeline (Milestone 3) works against standard **AcroForm** PDFs, proven with a synthetic IMM 5476 fixture. The actual high-volume IRCC forms (IMM 0008, 5257, 5645, 5669, 5406, 5532, 1294, 1295…) are distributed as **Adobe XFA "dynamic" PDFs**, which Apache PDFBox **cannot reliably fill or render**. Until each real form is triaged and onboarded, the feature can preview/validate data but cannot produce a correctly filled official PDF for those forms.

## 2. Background — AcroForm vs XFA
A PDF form can carry its fields in two very different ways:

- **AcroForm** — the ISO-standard PDF form model. Fields are PDF objects (`/AcroForm`, widget annotations). PDFBox reads and writes these natively. This is what our `PdfBoxFormEngine.fill(...)` targets.
- **XFA (XML Forms Architecture)** — an Adobe/LiveCycle layer where the form's fields, layout, and logic live in an **XML stream** inside the PDF (`/AcroForm /XFA`). Two flavours:
  - **Static XFA** — fixed layout; usually keeps a usable AcroForm "shadow" of the fields.
  - **Dynamic XFA** — layout is *rendered at open time* by an Adobe engine (rows grow, sections appear/disappear). The AcroForm shadow is often absent or stale; the visible document is generated from the XML.

IRCC's downloadable forms are predominantly **dynamic XFA** (the "Please wait… if this message is not eventually replaced" page is the dynamic-XFA loader). Many also embed a **2D barcode** that re-encodes the field values and is regenerated by Adobe Reader/LiveCycle on save.

## 3. Technical root cause — why PDFBox can't do it
- PDFBox is an **AcroForm** engine. It has **no XFA rendering/layout engine**.
- For a dynamic XFA form, writing values into the AcroForm fields (what `field.setValue(...)` does) **does not update the XFA XML**, so Adobe Reader renders the *unfilled* XFA and ignores our values — the user sees a blank form.
- The **2D barcode** is produced by Adobe's runtime from the XFA data; PDFBox cannot regenerate it. A submission expecting the barcode would be invalid.
- "Just strip the XFA" (`drop_xfa`) downgrades the form to its AcroForm shadow. Sometimes that yields a fillable static form; often the shadow is incomplete and the result is visually broken or missing fields.

**Net:** for dynamic XFA + barcode forms, only Adobe's own stack (LiveCycle / AEM Forms) — or a commercial SDK that licenses XFA handling — can fill *and* render correctly.

## 4. How it surfaces in our system today
- `PdfBoxFormEngine.inspect()` already detects this: `hasXfa = acroForm != null && acroForm.getXFA() != null`. It will report `hasXfa=true` and typically an **empty/partial field list** for dynamic XFA forms.
- `CaseFormGenerationService.generateOne()` only fills forms where `supportsFill = true`, so correctly-flagged XFA forms are safely **skipped**. But nothing sets that flag from real inspection yet (M6 inspect flow is deferred).
- **Danger case:** an XFA form mistakenly marked `supportsFill=true` → we generate a **blank-looking but "successful" PDF**, hash it, and present it as a draft. That is a correctness/trust failure, not just a missing feature.

## 5. Detection strategy (deterministic, per form)
During inspection, classify each source PDF:
1. `getXFA() == null` and AcroForm has fields → **STANDARD_ACROFORM** → `supportsFill=true`.
2. `getXFA() != null` but AcroForm has a complete field set matching the XFA → **STATIC_XFA** → candidate for *drop-XFA fill*; verify by round-trip.
3. `getXFA() != null` and AcroForm fields are empty/partial, or a dynamic-XFA flag is present → **DYNAMIC_XFA** → `supportsFill=false` / `status=BLOCKED`.
4. Has a 2D barcode (`supportsBarcode=true`) → treat as **BLOCKED** unless an Adobe/commercial engine regenerates the barcode.

Store the classification + inspected field count on `FormDefinition` (we already have `supportsFill`, `supportsBarcode`, `status`, `sourceSha256`).

## 6. Affected forms (from the researched list — confirm by inspection)
- **Likely standard/static AcroForm (try first):** IMM 5476, 5475, 5708, 5709, 5710.
- **Likely dynamic XFA / barcode (expect BLOCKED):** IMM 0008, 5257, 5645, 5669, 5406, 5532, 1294, 1295.
- **No PDF at all:** Express Entry (online-only) — checklist package, no fill.

## 7. Options considered
| Option | Fills dynamic XFA? | PII stays on-prem | Licensing | Effort |
|---|---|---|---|---|
| **A. PDFBox only + BLOCK XFA** | No (skips) | Yes | Apache 2.0 | Low |
| **B. PDFBox + drop-XFA for static XFA** | Partial | Yes | Apache 2.0 | Medium (per-form verify) |
| **C. Commercial engine for XFA subset** (Aspose.PDF / Qoppa, behind `PdfFormEngine`) | Yes | Yes | Paid | Medium |
| **D. Adobe AEM Forms / LiveCycle** | Yes (authoritative, incl. barcode) | Yes (on-prem) | Paid, heavy | High |
| **E. SaaS form-fill API** (Anvil/PDF.co) | No (AcroForm only) | No (PII egress) | Paid | Low |

- **E ruled out** — client PII must not leave the tenant, and they don't do XFA anyway.
- **iText ruled out** — AGPL would force open-sourcing the SaaS (commercial licence required otherwise).

## 8. Recommended approach (phased)
1. **Now / M6:** Build the inspect/triage flow. Inspect every candidate, auto-classify (§5), persist flags, and **BLOCK** dynamic-XFA/barcode forms with a clear reason. Makes behaviour correct and honest immediately (no blank "successful" drafts).
2. **Quick win:** For forms that inspect as standard/static AcroForm (likely 5476/5475/5708/5709/5710), enable fill via PDFBox (optionally drop-XFA for static) and verify each with a fixture round-trip.
3. **Later, if required:** Add a second `PdfFormEngine` implementation (Aspose.PDF or Qoppa — Java, on-prem, PII-safe) and **route only XFA forms** to it. The interface already isolates this; no caller changes.
4. **Degraded UX for BLOCKED forms:** produce a **"mapped values data sheet"** (canonical→field values as a printable PDF/HTML) so the consultant can transcribe into the official form manually — keeps the workflow useful where we can't fill.

## 9. Required changes by area
- **`FormDefinition` / catalogue (M6):** inspect endpoint `POST /api/forms/{formId}/inspect` → set `supportsFill`, `supportsBarcode`, `status` (`BLOCKED` for XFA), `sourceSha256`, and store classification (consider adding a `formTechnology` column: ACROFORM / STATIC_XFA / DYNAMIC_XFA / NONE).
- **`PdfBoxFormEngine`:** add `classify()` (or extend `PdfInspectionResult` with a `technology` enum + `fieldCount`); optional `dropXfaAndFill` path for static XFA.
- **`PdfInspectionResult`:** already has `hasXfa`; add classification + field count.
- **`CaseFormGenerationService`:** on BLOCKED/`supportsFill=false`, emit a clear draft outcome (notice draft or data-sheet fallback) instead of silently skipping.
- **Engine SPI:** introduce a second `PdfFormEngine` bean + selector (by `formTechnology`) if/when a commercial engine is added.
- **Frontend:** surface per-form "fillable / blocked (XFA) / manual data sheet" status in the drafts list and form catalogue.

## 10. Acceptance criteria
- Every onboarded form has inspection-derived `supports_fill`, `status`, `sourceSha256`, and technology classification.
- No dynamic-XFA form is ever marked fillable; generation never emits a blank-but-"successful" PDF.
- At least the AcroForm-compatible forms (target: 5476/5475/5708/5709/5710) generate correctly and are verified by a round-trip fixture.
- BLOCKED forms produce a clear consultant-facing reason and (optionally) a mapped-values data sheet.
- A documented decision on whether/when to license a commercial XFA engine.

## 11. Risks
- **Silent wrong output** if XFA detection is imperfect — mitigate with strict classification + a fill→reopen verification step.
- **Forms change without notice** — `sourceSha256` + edition tracking already mitigate; re-inspect on hash change.
- **Commercial engine cost/licensing** if XFA fill becomes a hard requirement.
- **Barcode forms** may be non-submittable even when filled unless Adobe regenerates the barcode (IRCC is phasing out barcode forms, which reduces this risk over time).

## 12. Effort estimate
- Inspect/triage + BLOCK + AcroForm subset working: **~3–5 days** (folds into M6).
- Static-XFA drop-and-fill verification: **+2–4 days** (per-form, variable).
- Commercial engine integration (if pursued): **~1–2 weeks** + procurement.

## 13. PoC results — validated 2026-06-29 (`pdf-xfa-poc/`)
A standalone PDFBox-3.0.3 PoC (sibling Maven project `pdf-xfa-poc/`) was run against the **real** IMM 5257 and IMM 5709. Findings:

- **Both are dynamic XFA** (`config` packet has `dynamicRender=required`) with only **2 AcroForm fields** (the validate/barcode fields). → The M3 AcroForm `fill()` path is useless for real IRCC forms; **datasets injection is mandatory**.
- The `datasets` packet (~520 KB for 5257) contains a large **`<LOVFile>`** (dropdown lookup tables) as a **sibling** of `<xfa:data>`. Scope all writes to the `xfa:data` node to avoid it.
- Under `xfa:data` the **applicant field nodes already exist (empty)** in a deep hierarchy, e.g. `form1/Page1/PersonalDetails/Name/FamilyName`, `…/DOBYear`, `form1/Page2/MaritalStatus/SectionA/Passport/PassportNum/PassportNum`.
- **Local-name matching is unsafe** — duplicate local names (FamilyName, Country, FromDate…) and same-name wrapper leaves (`<PassportNum><PassportNum/></PassportNum>`). → Mappings must store the **explicit XFA data path**, not an AcroForm field name.
- **IRCC PDFs are encrypted** (empty-password permissions / Reader-Extensions handler — the `PDFSecurity` packet). PDFBox `save()` throws unless `setAllSecurityToBeRemoved(true)` (which **decrypts → breaks usage rights**). `saveIncremental()` preserves the original bytes (encryption + Reader-Extensions) and appends the update.
- **Injection verified headlessly:** filling 4 values (incl. the nested PassportNum leaf) and re-reading the output datasets confirmed all values present in **both** the full-save and incremental-save outputs. Incremental output = original + ~89 KB appended.

**Still to verify in Adobe (manual):** open `pdf-xfa-poc/forms/imm5257-filled-incremental.pdf` and `-full.pdf` in Acrobat → (a) do values render in the dynamic form, (b) does **Validate** regenerate the 2D barcode, (c) does free Reader show "extended features disabled" (usage rights) — and does Acrobat Pro work regardless.

**Save-step wall (found when testing outputs in Adobe, 2026-06-29):** both filled outputs **fail to load / show a certificate error in Adobe**. Root cause: IRCC forms are **encrypted + certified (DocMDP) + Reader-Extended**, and PDFBox has open bugs writing encrypted incremental updates ([PDFBOX-3188](https://issues.apache.org/jira/browse/PDFBOX-3188), [PDFBOX-4286](https://issues.apache.org/jira/browse/PDFBOX-4286)) → appended objects aren't encrypted correctly (Adobe can't open). Full save decrypts+rewrites → breaks certification + dynamic XFA. **Conclusion: pure PDFBox can inject XFA data but cannot re-save these encrypted+certified forms into an Adobe-valid file.** Producing a valid filled XFA needs append-mode + encryption + DocMDP handling: **iText 7 (commercial licence; AGPL otherwise) or Aspose.PDF / Qoppa**, or Adobe AEM/LiveCycle. Recommended $0 path: **data-sheet fallback** (emit a mapped-values sheet the consultant types into the official form in Adobe, which handles barcode/cert natively) for XFA forms, and keep PDFBox AcroForm fill only for genuinely-AcroForm forms (5476/5475/5708-5710, TBC by inspect).

**Confirmed backend implications:**
- Add an XFA fill path (datasets injection + `saveIncremental`) as a second `PdfFormEngine` strategy, selected by form technology.
- `FormFieldMapping`/`FormFieldDefinition` need an **`xfaDataPath`** (e.g. `form1.Page1.PersonalDetails.Name.FamilyName`) for XFA forms, distinct from AcroForm `pdfFieldName`.
- The M6 inspect flow must **dump the `xfa:data` skeleton** so mappings can target real data paths.
- Prefer incremental save to keep usage rights; document the consultant step "open in Adobe Acrobat and click Validate to generate the barcode."
- Filled XFA won't render in browser/PDFBox previews — rely on the existing mapped-value UI for review; Adobe is the source of truth.

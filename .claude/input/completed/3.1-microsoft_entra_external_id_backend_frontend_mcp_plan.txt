I'll lay out this as an implementation plan across three parts: frontend login, backend/API token validation, and MCP server
authorization. I'll also verify current Microsoft/Spring details so the plan does not rely on stale setup assumptions.

Target architecture

    User / AI Agent
          -> OAuth2/OIDC login

    Microsoft Entra External ID
          -> access token

    Frontend
          -> Bearer token

    Backend API
For MCP:

    AI Agent / MCP Client
          -> OAuth2/OIDC login

    Microsoft Entra External ID
          -> Bearer token

    MCP Server
          -> calls backend APIs with user context

    Backend API
Your session login can still exist for your normal web dashboard if you want, but for frontend SPA/API/MCP usage, the cleaner
long-term model is:

    Frontend -> access token -> Backend API
    AI Agent -> access token -> MCP Server
    MCP Server -> access token / internal token -> Backend API
Microsoft OAuth2 authorization code flow is intended for apps that need authorized access to protected resources like web
APIs, and Microsoft recommends exposing API scopes when protecting your own APIs. [1]

Step 3: Frontend changes

Your frontend needs to replace custom login/API key behavior with Microsoft login.

Frontend responsibilities

1. Redirect user to Microsoft Entra External ID login
2. Receive auth code
3. Exchange code using PKCE
4. Store access token safely in memory
5. Call backend APIs with Bearer token
6. Refresh token silently where supported
7. Logout user from app and identity provider

For Angular/React, use MSAL browser.

Conceptually:

    const loginRequest = {
        scopes: [
            "openid",
            "profile",
            "email",
            "api://immigration-saas-api/cases.read",
            "api://immigration-saas-api/documents.read"
        ]

    };
API call:

    GET /api/cases
    Authorization: Bearer <access_token>

Frontend pages affected

    Login page
    Auth callback page
    Logout handler
    Token acquisition service
    Route guard
    API HTTP interceptor
    User profile display
    Unauthorized / consent required page

Important frontend decision

For a simple SaaS frontend, I recommend:

    Frontend uses MSAL
    Backend validates JWT
    No backend session needed for API calls
This is cleaner than mixing frontend session cookies and OAuth tokens.

Step 5: Add application-level authorization

OAuth token validation only proves:

    This user is authenticated
    This token was issued by your trusted Entra tenant
    This token has certain scopes
It does not automatically prove:

    User can access this specific immigration case
    User belongs to this consultant account
    User belongs to this tenant
    User can view this client document
So you still need your own database-level authorization.

    public CaseDto getCase(String caseId) {
            String entraUserId = SecurityContextHolder.getContext()
                   .getAuthentication()
                   .getName();

            AppUser user = userRepository.findByExternalSubject(entraUserId)
                   .orElseThrow();

            CaseEntity caseEntity = caseRepository.findById(caseId)
                   .orElseThrow();

            if (!caseAccessService.canReadCase(user, caseEntity)) {
                   throw new AccessDeniedException("No access to case");

            }

            return mapper.toDto(caseEntity);
    }

Step 6: MCP server changes

Your MCP server should also become an OAuth2 Resource Server.

Current MCP authorization guidance says MCP servers must expose OAuth 2.0 Protected Resource Metadata and include
authorization server information. [4]

So your MCP server should support:

    Bearer token validation
    Protected resource metadata
    Tool-level authorization
    User-level audit logging

MCP server auth flow

    AI Agent / MCP Client
          -> connects to MCP server

    MCP server says auth is required
          ->

    MCP client opens Microsoft login
          ->

    User logs in
          ->

    MCP client receives access token
          ->

    MCP client calls tools using Bearer token
Tool call:

    POST /mcp
    Authorization: Bearer <access_token>

Step 10: MCP server calling backend APIs

You have two main options.

Option A: MCP passes user token to backend

    AI agent
          -> user access token for backend API

    MCP server
          -> same token

    Backend API
This only works cleanly if the token audience is accepted by the backend API.

But normally, OAuth access tokens are audience-specific:

    Token for MCP server -> audience api://immigration-saas-mcp
    Token for backend API -> audience api://immigration-saas-api
So passing the MCP token directly to the backend may fail if the backend validates audience strictly.

Option B: MCP uses On-Behalf-Of flow

This is the better standards-based approach:

    AI agent gives token to MCP server
    MCP server exchanges it for backend API token
    MCP server calls backend API

                                                                Microsoft Entra External ID Plan
Microsoft OAuth2 On-Behalf-Of flow is designed for the scenario where a web API calls another web API using the user identity
and permissions. [5]

Flow:

    User token for MCP server
          ->

    MCP server uses OBO
          ->

    New token for backend API
          ->

    Backend validates token
This is the cleaner production design.

Option C: Internal service token + user context

For MVP, this can be simpler:

    MCP validates user token
    MCP calls backend using internal service credential
    MCP includes user ID in signed/internal header
    Backend trusts MCP only from private network
Example:

    Authorization: Bearer <internal_service_token>
    X-User-Subject: <entra-user-sub>
    X-Tenant-Id: <tenant-id>
    X-Request-Source: mcp-server
But you must protect this strongly:

    private networking
    backend only accepts this from MCP server
    signed headers or mTLS if possible
    audit logging
    no public trust of X-User-* headers
For your early Azure MVP, I would choose:

    Phase 1: MCP validates user token and calls backend with internal service credential
    Phase 2: Move to Microsoft OBO flow
OBO is better, but internal service auth is easier for a first working version.
